# ДЗ 3. Переобучение модели в Airflow

## Запуск

Нужны Docker Desktop и Docker Compose. Для Docker желательно выделить 8 ГБ памяти.
Скачайте репозиторий и перейдите в его папку:

```bash
git clone https://github.com/AnzhelikaSakhautdinova/ml-fraud-airflow.git
cd ml-fraud-airflow
docker compose up -d --build
docker compose ps -a
```

Первый запуск занимает несколько минут. Контейнеры `init` и `kafka-init`
должны завершиться с кодом 0, остальные — работать.
`init` загружает данные, обучает первую модель и настраивает Airflow.

Airflow: http://localhost:8083 — логин `admin`, пароль `admin`.
Все дальнейшие команды выполняются из корня репозитория.

## Как устроено

Сервис читает транзакции из Kafka, обрабатывает признаки и считает скор
с помощью CatBoost на CPU. Результат отправляется в топик `scores`:

```json
{"transaction_id":"example","score":0.15,"fraud_flag":0,"model_version":"2020-05-checksum"}
```

Препроцессинг находится в `app/features.py`: циклические признаки часа и дня
недели, признаки ночи и выходного, преобразования суммы, разности координат,
население и категории. Один и тот же код используется при обучении и скоринге.
Порог фрода — 0.5. Модель небольшая: 80 деревьев глубины 4.

В Airflow три DAG, каждый запускается раз в 5 минут. `catchup=False`:

| DAG | Что делает |
|---|---|
| `supply_labeled_month` | Добавляет следующий месяц и удаляет старую историю |
| `retrain_fraud_model` | Готовит окно → обучает → сравнивает модели → принимает решение о публикации |
| `data_quality_report` | Проверяет данные и сохраняет HTML-отчёт |

Файлы DAG лежат в `dags/`, функции задач с docstring — в `pipeline/`.
Airflow и сервис скоринга используют общую папку в Docker-томе `runtime`.
В ней находятся размеченная витрина SQLite, модели, результаты обучения и отчёты.
Метаданные Airflow хранятся отдельно. Для небольшого стенда выбран SequentialExecutor.

## Данные и переобучение

В `data/seed.csv` включены 9000 строк из train.csv соревнования:
по 3000 за январь, февраль и март 2020 года, выборка с seed=42.
Полный датасет для запуска не нужен. Происхождение данных — [ATTRIBUTION.md](ATTRIBUTION.md).

Новый месяц имитируется сдвигом дат уже существующих строк. День и время
сохраняются; если такого дня в новом месяце нет, берётся его последний день.
Метки фрода сохраняются.

- Размер нового батча — 3000 строк.
- Глубина истории — 36 месяцев.
- Окно обучения — 3 месяца: два ранних идут в train, последний — в test.
- Случайного разбиения на train/test нет.

Кандидат и текущая модель сравниваются на одних и тех же строках последнего
месяца по **Average Precision**. Если AP кандидата ниже, он не публикуется.
При равной или большей AP публикуется новая версия. ROC AUC записывается
дополнительно. Порог на test не подбирается.

Версия переключается через атомарную запись `models/active.json`, после сохранения
бинарника. Скоринг проверяет указатель перед каждым сообщением и загружает новую
модель без перезапуска контейнера. В `scores` записывается использованная версия.

Повторная загрузка не дублирует месяц. После сбоя используются те же сохранённые
train/test; месяц отмечается обработанным после сохранения решения. При отказе
по качеству остаётся старая модель, но обработанный месяц учитывается, чтобы
можно было перейти к следующему. Решения сохраняются в `runtime/decisions/`.

Будущие месяцы синтетические и повторяют исходные операции, поэтому эти метрики
нельзя считать независимой оценкой качества на реальных будущих данных.

## Как проверить

В Airflow вручную запустить `supply_labeled_month`, дождаться успеха,
затем `retrain_fraud_model` и `data_quality_report`. Для запуска используется
кнопка Trigger DAG. У DAG переобучения должны завершиться все четыре задачи.
Если нового месяца ещё нет, подготовка окна пропускается.

Отправить пример в Kafka и посмотреть результаты:

```bash
docker compose exec -T scorer python -m scripts.send_csv
docker compose exec kafka kafka-console-consumer --bootstrap-server kafka:9092 --topic scores --from-beginning --max-messages 5
```

Эта команда читает с начала топика и может показать старые версии.
Для просмотра новых сообщений запустите consumer без `--from-beginning`
в одном терминале, затем отправьте пример в другом. Сравните `model_version`
до и после принятого обновления. Если кандидат отвергнут, версия останется прежней.

Автоматические проверки:

```bash
docker compose exec -T airflow python -m unittest discover -s tests -v
docker compose exec -T airflow python -m scripts.check_system
```

Первый набор проверяет окно, повторы, отказ худшей модели, сбой публикации,
горячую загрузку и DQ. Второй запускает DAG через API и проверяет реальный
скоринг через Kafka. Он временно управляет паузами DAG и в конце включает расписания.

## Data Quality

Проверяются 10 правил:

1. Витрина не пустая.
2. ID уникальны.
3. Даты корректны.
4. Месяц записи совпадает с датой транзакции.
5. `target` содержит только 0 и 1.
6. Числовые значения конечны.
7. Сумма и население неотрицательные.
8. Координаты в допустимых пределах.
9. Категории не пустые.
10. В каждом месяце есть оба класса.

HTML сохраняется в `runtime/reports/dq.html`, рядом с каталогом моделей.
При нарушении правила отчёт показывает FAIL, а задача завершается ошибкой.
Чтобы скопировать актуальный отчёт на ноутбук:

```bash
docker compose cp airflow:/opt/project/runtime/reports/dq.html reports/dq.html
```

Открыть `reports/dq.html` в браузере. Метрики и текущий указатель можно скопировать так:

```bash
docker compose cp airflow:/opt/project/runtime/models/active.json reports/active.json
```

## Логи и остановка

```bash
docker compose logs --tail=100 init airflow scorer
docker compose exec -T airflow airflow dags list-import-errors
docker compose down
```

Данные и модели сохраняются. `docker compose down -v` полностью удаляет тома проекта.
Порт 8083 должен быть свободен. Логин admin/admin используется только для локального запуска.
